# NEURON: The Complete Technical Blueprint

## 1. Anatomy of the Adaptive Engine
The Adaptive Engine is not a single function; it is a **Closed-Loop Feedback System** composed of four interacting sub-components.

### 1.1 The Activity Observer (The "Eyes")
*   **Role**: Transparently instruments the `Memory` class.
*   **Action**: Every time a `process()` or `retrieve()` call is made, the Observer writes a lightweight record to the `activity_log`.
*   **Data Captured**: `user_id`, `activity_type` (READ/WRITE), `timestamp`, and `node_count`.

### 1.2 The Fitness Evaluator (The "Judge")
*   **Role**: Converts raw activity into a performance score.
*   **Action**: During the "Sleep" cycle, it reviews the `retrieval_events`. It combines **Explicit Human Feedback** (Thumbs Up/Down) with **Implicit Heuristics** (Coverage, Confidence, and LLM-Judging).
*   **Output**: A 0.0 - 1.0 "Success Grade" for every retrieval strategy.

### 1.3 The Evolutionary Strategist (The "Brain")
*   **Role**: Manages the population of search parameters.
*   **Action**: It uses an **ε-greedy algorithm** to pick the best strategy for the user. Every 24 hours, it performs a "Mutation":
    *   **The Cull**: Deletes strategies with low rolling-average fitness.
    *   **The Mutation**: Takes the "Winning" strategy and creates a child with slightly different `k_seeds`, `depth`, or `min_weight`.
*   **Goal**: To discover the optimal search settings for your specific data distribution.

### 1.4 The Sleep Consolidator (The "Optimizer")
*   **Role**: Performs heavy graph maintenance during idle periods.
*   **Action**: 
    *   **Read-Driven Myelination**: Strengthens edges that were part of successful retrievals.
    *   **Usage-Aware Pruning**: Archives nodes that haven't been "touched" by the retriever in weeks, regardless of their age.
    *   **Belief Merging**: Consolidates dense clusters of new information into "Master Beliefs."

## 2. Core Logic & Data Models

### 1.1 The Node Schema (Memories)
Every memory in NEURON is an "Atomic Belief."
*   **`label`**: The distilled fact (e.g., "Paris is the capital of France").
*   **`embedding`**: A 384-dimensional vector generated by `all-MiniLM-L6-v2`.
*   **`confidence`**: A floating-point (0.0 - 1.0) representing the system's certainty.
    *   *Default*: 0.6
    *   *Growth Formula*: $C_{new} = C_{old} + (1.0 - C_{old}) \times 0.1$
*   **`evidence_count`**: Integer representing how many times this fact has been re-confirmed by the user.

### 1.2 The Edge Schema (Relationships)
Edges represent the "Highways" between nodes.
*   **`relation`**: Categorical (e.g., `supports`, `contradicts`, `causes`, `refines`).
*   **`weight`**: The traversal probability (0.0 - 1.0).
    *   *Standard/Fast Initial*: 0.5 or 0.4.
    *   *Deep Initial*: Dictated by LLM reasoning (0.1 - 0.95).
*   **`evidence_count`**: Incremented every time the system detects this specific relationship being repeated in new text.

## 3. The Data Addition Lifecycle: Step-by-Step

### 3.1 Standard `process(text)` (Real-Time Ingestion)
*   **Step 1: Embedding**: The text is converted into a 384-dimensional vector using the `SentenceTransformer` (all-MiniLM-L6-v2).
*   **Step 2: Neighborhood Search**: The system runs a **Cosine Similarity** search against the database.
*   **Step 3: The 0.85 Decision**:
    *   **Match Found**: If similarity > 0.85, the system increments the `evidence_count` of the existing node. Confidence is boosted using the **Asymptotic Formula**: $C_{new} = C_{old} + (1.0 - C_{old}) \times 0.1$.
    *   **No Match**: A new node is created with a default confidence of 0.6.
*   **Step 4: Relationship Discovery (LLM)**: The LLM analyzes the new node against its 5 closest neighbors to identify logical links (`supports`, `contradicts`, etc.).
*   **Step 5: Edge Creation**: Edges are saved with an initial weight of 0.5.

### 3.2 Fast `process_batch(texts)` (High-Throughput)
*   **Step 1: Vectorized Embedding**: All texts are embedded in a single batch operation for maximum GPU/CPU efficiency.
*   **Step 2: Internal Deduplication**: The system checks for semantic repeats *within the batch itself* to avoid redundant nodes.
*   **Step 3: Bulk Upsert**: Using a single SQL/Cypher transaction, the system performs a **"Match-or-Insert"** for all nodes in the batch.
*   **Step 4: Rapid Weighting**: Edges are initialized at 0.4. If the same relationship appears 5 times in the batch, the weight is compounded immediately.

### 3.3 Deep `process(text, deep=True)` (High-IQ Ingestion)
*   **Step 1: Semantic Chunking**: A Reasoning LLM breaks the input into "Atomic Beliefs" (short, single-fact sentences).
*   **Step 2: Metadata Extraction**: For each belief, the LLM extracts:
    *   **Entities**: (e.g., `["Tim Cook", "Apple"]`)
    *   **Temporal Stability**: (e.g., "Fact is permanent")
    *   **Abstraction**: (e.g., "Fact is a high-level principle")
*   **Step 3: Logic-Driven Weighting**: The LLM assigns a custom weight (0.1 to 0.95) based on the **Strength of Influence** it detects between nodes.
*   **Step 4: Contradiction Check**: The LLM proactively searches for opposing facts in the graph to resolve conflicts before they are retrieved.

## 4. Adaptive Memory Ecosystem

### 4.1 The 0.85 Threshold (Gatekeeping)
Whenever new text enters the brain, the system runs a **Vector Similarity Search** against existing nodes.
1.  **Similarity > 0.85**: The system considers this a **Confirmation**. It does NOT create a new node. It increments the `evidence_count` of the existing node and boosts its `confidence`.
2.  **Similarity < 0.85**: The system considers this **New Information**. It creates a fresh node with default confidence (0.6).

### 2.2 Mode Comparison
| Mode | Method | Weight Logic | Metadata Depth |
| :--- | :--- | :--- | :--- |
| **Standard** | `process()` | Static 0.5 | Basic (Label + Embedding) |
| **Fast** | `process_batch()` | Static 0.4 | Minimal (Bulk deduplication only) |
| **Deep** | `deep=True` | **Dynamic** | Full (Entities, Temporal, Abstraction) |

## 3. Retrieval & The Adaptive Brain (The "Read" Side)

### 3.1 The "Walk" Algorithm
When you call `retrieve()`, NEURON performs a multi-step search:
1.  **Seed Search**: Find the Top-K (`k_seeds`) nodes using Vector Similarity.
2.  **Graph Traversal**: Starting from each seed, explore neighbors up to `traversal_depth`.
3.  **Path Scoring**: Each neighbor is ranked using the formula:
    $PathScore = (Similarity \times 0.4) + (EdgeWeight \times 0.6)$

### 3.2 Adaptive Mode Scenarios
#### Scenario A: Automated (Hands-off)
*   **Setup**: `ENABLE_ADAPTIVE_MEMORY=True`, `ADAPTIVE_MODE=auto`
*   **Behavior**: A background daemon thread manages everything.
*   **Example**: You chat with your bot all day. At night, the bot "dreams" (reviews logs), strengthens the paths that helped you, and prunes the paths that were useless.

#### Scenario B: Manual (Developer Controlled)
*   **Setup**: `ADAPTIVE_MODE=manual`
*   **Behavior**: You log activity, but the system only optimizes when you call `brain.force_sleep()`.
*   **Use-case**: High-scale enterprise apps that want to trigger maintenance only during server idle time.

## 4. The Feedback Loop (Delayed Training)

Since users can't rate a retrieval before they see the answer, NEURON uses a **Delayed Feedback Pattern**:

```python
# Step 1: Retrieval (System provides an ID)
result = brain.retrieve("Why is the sky blue?", user_id="u1")
event_id = result["event_id"]

# Step 2: Generation (You use the context to answer)
# ... your LLM logic here ...

# Step 3: Feedback (User rates the answer)
# This teaches the system which Retrieval Strategy worked!
brain.submit_feedback(event_id, score=1.0)
```

## 5. Strategy Evolution (Survival of the Fittest)

NEURON maintains a population of **Retrieval Strategies**. A strategy is a combination of:
*   `k_seeds` (Width of search)
*   `traversal_depth` (Depth of search)
*   `min_edge_weight` (Strictness of search)

### The Fitness Proof (EMA Math)
A strategy's fitness is updated using an Exponential Moving Average (EMA). This prevents a single bad user query from killing a good strategy.
$Fitness_{new} = (Fitness_{old} \times 0.7) + (NewEventScore \times 0.3)$

### The Mutation Cycle
Every `MAINTENANCE_INTERVAL_HOURS`:
1.  **Identify the Loser**: The strategy with the lowest fitness is deleted.
2.  **Identify the Winner**: The strategy with the highest fitness is cloned.
3.  **Mutate**: The clone is slightly altered (e.g., if depth was 3, the child gets depth 4).
4.  **Repeat**: Over weeks, your memory engine evolves toward the perfect search logic for your specific data.

## 6. Advanced Diagnostics
You can monitor the "Brain Health" of any user:
```python
health = brain.graph_health(user_id="u1")
# Returns:
# {
#   "total_nodes": 1250,
#   "confidence_ratio": 0.82, # Average confidence
#   "prune_ratio": 0.05,      # % of nodes near archiving
#   "status": "healthy"       # or 'cluttered', 'decaying'
# }
```

### `process_batch(texts, user_id)`
High-speed ingestion for large datasets.
*   **Arguments**: List of strings and a user ID.
*   **Performance**: 10-20x faster than individual `process` calls.

### `search_archive(query, user_id)`
The "Deep Recall" feature. Searches only through `deprecated=True` nodes.
*   **Use-case**: Use this when a standard `retrieve` fails to find an answer. It digs into "forgotten" memories.

### `strategy_report()`
Returns a list of all current retrieval strategies in the population, including their `k_seeds`, `depth`, and `fitness_score`.

### Per-User Isolation
NEURON uses `user_id` to namespace all data. Every node, edge, activity log, and retrieval event is scoped to a `user_id`. For **complete** per-user configuration isolation (e.g., different adaptive settings per user tier), create a separate `AdaptiveMemory` instance pointed at a different `DATABASE_URL`. This is the cleanest and most production-safe approach.
